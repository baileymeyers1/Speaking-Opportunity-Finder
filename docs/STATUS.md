## What's Working
- Browse, filters, saved opportunities, saved searches, auth (JWT cookie).
- **Database: Postgres everywhere.** `docker compose up -d db` starts `postgres:16` on host port 5433 with `speaking_finder` (dev) and `speaking_finder_test` (vitest). One schema, `prisma/schema.prisma`; `prisma.config.ts` holds the schema path and `DATABASE_URL` for the CLI. The Prisma 7 client is generated into `server/src/generated/prisma` (gitignored; `npx prisma generate`), imported from there, and built once in `server/src/lib/prisma.ts` on `PrismaPg` (a lazy `pg` pool). `tsc` compiles the generated TypeScript into `server/dist`; the query compiler is a base64 WebAssembly import from `@prisma/client/runtime`, so the Vercel function needs no extra files. Search is case-insensitive (`mode: 'insensitive'`, no provider sniffing); industry filter matches the exact JSON token.
- **Server tests against a real Postgres.** `server/vitest.config.ts` points `DATABASE_URL` at the test database and a global setup pushes the schema into it; `enrichmentBudget.db.test.ts` exercises the budget counter and the claim lock for real, every other suite mocks `lib/prisma.js`.
- **Admin dashboard** (`/admin/dashboard`, `client/src/components/admin/`): an attention strip derived on the client (`attention.ts`) from the sources and pipeline responses, then Sources (status, last run, 14-day sparkline, row counts, "Run now" via `POST /api/sync?mode=<cadence>&scraper=<name>`), Pipeline (unenriched backlog, claims and stale claims, failures, verification due per `verification.ts`, today's budget meter, cron liveness, last 10 events, "Run enrichment batch now" via `POST /api/admin/enrichment/run`), Catalogue (active rows by format, industry, deadline bucket, remote) and Demand (saved-search filters plus the live-search log's 7/30-day totals and top queries). Endpoints: `GET /api/admin/analytics/{sources,pipeline,catalogue,demand,search-log}` in `server/src/services/analytics/`, typed in `shared/admin.ts`. Red conditions: a source with 3 consecutive empty/error runs, budget exhausted, any stale claim, >50 rows overdue for verification, daily sync older than 26h, weekly older than 8d, enrichment older than 15 min while work is queued.
- **Hosting: Vercel only.** Express runs as one serverless function; Vercel Cron drives syncs and enrichment. The build runs `prisma generate`, `prisma db push` against the production `DATABASE_URL`, then `npm run build`, so schema changes deploy themselves (preview builds included).
- **Scrapers** (registry in `server/src/scrapers/index.ts`): confs.tech, javaconferences.org, callingallpapers.com, developers.events, pretalx.com, sessionize.com, linkup (daily); wikicfp.com, conferencealerts.com (weekly). papercall.io was removed: the domain no longer resolves. Each run persists its own rows and is recorded in `ScraperRun` (surfaced by `GET /api/admin/analytics/sources`; a source missing from the registry shows as retired). Syncs take a time budget (50s under cron) and run least-recently-run sources first, so nothing starves.
- **Pretalx** (`scrapers/pretalx.ts`): `GET {instance}/api/events/` is a flat public list (pretalx.com: 755 events, ~83 upcoming); each upcoming event's `/{slug}/cfp` page gives open/closed (the submit button) and the deadline (a localized status line). Instances: pretalx.com and pretalx.c3voc.de. Live 2026-11-03: 39 open calls in 3.5s. The API has no location; enrichment fills it.
- **Sessionize** (`scrapers/sessionize.ts`): the Discover listing needs a login, but `sitemap/events.xml` lists ~11,000 public event pages newest first and each page states CFP open/close dates, event date(s), location and website. Each run reads the newest 80 pages; recurring user groups are labelled `meetup`. Live 2026-11-03: 74 open calls (56 conference, 18 meetup) in 3.0s.
- **Linkup query set** (`scrapers/linkupQueries.ts`, 110 queries): 89 industry conference queries plus a format group (8 podcast guest calls, 6 meetup/user-group, 4 webinar, 3 panel), each stored with its `format`. The daily run takes a 6-query rotating slice plus up to 2 promoted queries.
- **Search log** (`services/searchLog.ts`, model `SearchLog`): both live-search controllers await one insert per search (query normalized, industries/locations JSON, result count, user id when signed in). `promotedLinkupQueries` returns the most frequent normalized queries of the last 30 days, searched at least twice and not in the static set, as `"<query> call for speakers CFP <years>"`. `GET /api/admin/analytics/search-log` (`analytics/searchLog.ts`) returns 7/30-day totals and the top queries, which the admin Demand section renders.
- **One extraction call** (`server/src/services/extraction.ts`, Anthropic SDK 1.x, API version 2026-10-21): structured outputs (`output_config.format`, strict JSON schema) on `claude-haiku-5-5` return typed dates, location, closed/relevant flags, compensation, format, industries, cleaned title/organization and a high/medium/low confidence per date field. `mergeExtraction` holds the single set of merge rules. Enrichment, verification and live search all go through it.
- **Deadline semantics** (`server/src/lib/deadlines.ts`, pure, also imported by `client/src/lib/dates.ts`): a CFP deadline is a calendar day in a zone, stored as the instant that day ends (`endOfDayInZone`) with the zone in `deadlineTimezone` (IANA name or `AoE`; null = not stated, read as AoE, UTC-12, the most lenient reading). The extraction returns `cfpDeadline` + `cfpDeadlineTime` + `deadlineTimezone` (never inferred from the venue); scrapers go through `endOfCalendarDay`; Pretalx uses the event's API `timezone`, Sessionize the exact closing instant it embeds (`Etc/GMT±N`), callingallpapers its ISO offset. `deadlineInstant` reads a not-yet-migrated midnight-UTC row as AoE end of day, so nothing expires early before or after the migration. `cleanupExpired` only deletes rows closed for 36h+. Cards show "3d left" with the closing time in its zone and on the viewer's clock on hover; the detail page shows "Monday, November 30, 2026, 11:59 PM AoE · Dec 1, 3:59 AM your time".
- **Background enrichment** fetches `applyUrl` first (`services/pageText.ts`, 8s, 5000 visible chars) and extracts from the page text; a 404/410 closes the row without a Claude call. DB-backed daily budget (200 calls), per-row claim lock, 3 retries, 50s time budget per cron run. Re-scrapes preserve enriched fields. Cleanup never deletes saved rows. Closed/irrelevant rows are flagged in columns and hidden.
- **Scheduled verification** (`services/verification.ts`): once no unenriched rows remain, the same cron re-checks stored listings against their page. Deadlines within 14 days are re-checked every 2 days, everything visible weekly; dates, location, remote flag, compensation and `isClosed` follow the page; `verifiedAt` / `verificationError` / `dateConfidence` are stored. Same daily budget.
- **Live search** runs one Linkup page per query variant in parallel, dedupes by URL, enriches only the top 8 synchronously (page fetch + extraction) and persists every hit inside the request as `source: 'Live Search'`; the rest are stored with `enrichmentStatus: null` for the worker. Measured: 15 results in 10.6s against the real APIs.
- **Client** shows "Verified Xd ago" on cards and the detail page, and renders low-confidence dates as "~Dec 1, 2026" with a tooltip (`components/VerificationHints.tsx`).
- **Client data flow:** the URL is the only filter state (`client/src/filters/serialize.ts`); TanStack Query owns fetching and caching (`client/src/hooks/`), with public lists persisted to localStorage for instant cold starts. Same URL = same cache key, so back navigation restores the prior list and any filter change refetches, live results included. Live search is a mutation that replaces the list entry for its filters.
- **Shared wire types** in `shared/types.ts`, re-exported by the client and used to type the server's opportunity responses. `npm run lint` (ESLint 9, root `eslint.config.js`) passes; client unit tests run under `TZ=America/Los_Angeles` so UTC date formatting is asserted.
- **Speaker profile and match score.** `SpeakerProfile` (one per user: topics, bio, seniority, home city/country, travel radius, remote preference, compensation requirement, preferred formats) is edited at `/profile` and stored via `GET/PUT /api/profile` (zod-validated, `services/profileService.ts`). `services/matchScore.ts` scores a row 0..100 from the profile alone, no model call: topic overlap (whole-word, case-insensitive, plural-tolerant, against industries + title + description), location fit (remote preference, same city/country, travel radius; "City, ST" counts as US), compensation fit, format fit, each counted only when the profile states it; 20% quality blended in; small penalties for a deadline inside 3 days, a low-confidence deadline and an unverified row. Reasons ("matches: devops", "in Denver", "travel covered") and misses ("in-person in Berlin, you prefer remote") travel with the row. The list and detail routes read an optional token; `sort=match` scores a quality-first candidate set of up to 500 rows in memory and paginates it. Client: "N% match" popover on cards, "Why this matches" on the detail page, "Best match" in the sort select once a profile exists; login/logout/profile save drop cached lists so scores never leak between users.

## Deploy Gotchas
- Every Vercel build, previews included, runs `prisma db push` against the production database. Before pushing a branch with a schema change, diff it against production: `vercel env pull --environment=production <file>`, then `npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema prisma/schema.prisma --script` must print an empty migration (or exactly the additive change you intend). A destructive change makes the build fail (no `--accept-data-loss`), it does not drop data.
- `prisma` on npm has an 8.0 release candidate as `latest`; `prisma`, `@prisma/client` and `@prisma/adapter-pg` are pinned to `^7.10.1`. Prisma 7's CLI refuses `db push --accept-data-loss` and `--force-reset` when run by an AI coding agent; run those from your own terminal.
- Env vars live in the Vercel dashboard: `DATABASE_URL`, `JWT_SECRET`, `CRON_SECRET`, `ANTHROPIC_API_KEY`, `WEB_SEARCH_API_KEY`. No `CLAUDE_MODEL` override is set; if you add one it must be a current model (the request sends `output_config.effort`).
- The team is on Vercel Pro, so the 5-minute enrichment cron runs as declared (verified 2026-11-03: ~12 invocations/hour in runtime logs). Express trusts Vercel's proxy (`trust proxy` when `VERCEL` is set) so rate limiting keys on the real client address.
- `npm audit` still reports 18 advisories (16 moderate, 2 high), all behind major bumps that were deliberately not taken here: react-router-dom 7 (open redirect / SSR hydration in react-router 6), Vite 8 (dev-server path traversal, `launch-editor` on Windows, the esbuild dev-server CORS issue), ESLint 10 / typescript-eslint and nodemon (the `minimatch` globparts DoS), and `picomatch` 2.x reached through Playwright. None of them ships in the production bundle or runs on Vercel.

## Known Issues & Tech Debt
- A 401 from any protected endpoint now clears the signed-in user and sends protected pages to login (`api:unauthorized` event from `client/src/api/client.ts`); the in-app browser pane shares one localhost cookie jar across sessions, so a stale `token` cookie from another worktree's test login is the usual cause of a surprise logout in dev.
- Live search Claude calls (up to 8 per request) are not counted against the daily enrichment budget; only the worker's are.
- Verification spends whatever budget enrichment leaves each day; with ~1,400 cron slots/day and a 200-call cap, the cap is the real limit.
- `express-rate-limit` uses the in-memory store, which does nothing on serverless.
- Password reset only logs the token to the console.
- Production rows written before the deadline-timezone change still hold midnight UTC with no zone until `shiftLegacyDeadlines.ts` is run against production (see Environment Notes); they are read correctly in the meantime, but the SQL filters (`cfpDeadline >= now`) still flip at UTC midnight for them.
- A live-search snippet or a scraped page with an offset no Etc zone covers (e.g. +05:30) stores the exact instant with `deadlineTimezone` null, so its time is labelled in AoE terms (true, but odd-looking).
- Rate limiters are skipped in development and use the in-memory store in production, which does nothing across serverless instances.
- The Playwright auth/saved specs register accounts with `test-${Date.now()}@example.com`; two workers starting in the same millisecond collide, so one of them fails now and then under `fullyParallel`.
- conferencealerts.com is a general conference directory; rows kept are those with an open abstract deadline, and some are expos whose deadline equals the event date. WikiCFP rows are academic calls for papers.
- About a fifth of open Pretalx calls set no deadline in Pretalx (the submit button is live, the status line is empty or only in prose); they are stored without `cfpDeadline` and verification closes them from the page text. Pretalx events carry no location, Sessionize rows no industries, until enrichment runs.
- Sessionize reads only the newest 80 event pages per run (~4 new events a day), so an older call that reopens is picked up by verification, not by the scraper.
- The daily cron now has 7 daily sources for a 50s budget; the least-recently-run ordering means a slow day skips one or two, which run first the next day.
- Rows enriched before verification shipped have `verifiedAt = null` and are picked up by the weekly sweep, oldest first.
- Match scores live in the opportunity list responses, which are cached under the filter key and persisted to localStorage for anonymous visitors. A returning user whose cookie is still valid and whose persisted list is under 5 minutes old sees that list without scores until it refetches. Login, logout and a profile save invalidate the lists.
- `sort=match` with a search term ranks all search matches by score (no 500 cap); without one it caps the candidate set at 500 quality-first rows, so `total` is capped too.
- Cron liveness is inferred: the 5-minute enrichment cron leaves no trace of its own, so the dashboard reads the newest `enrichedAt`/`verifiedAt` and only calls it dead while work is queued. "Closed this week" uses `updatedAt` on closed rows because there is no `closedAt` column.
- `POST /api/sync` keeps an in-memory "already syncing" flag, which does nothing across serverless instances; two admins clicking "Run now" at once would run the scraper twice.
- The local dev database starts empty: run a sync (`POST /api/sync?mode=daily&scraper=confs.tech` as admin, or `npm run prisma:seed` for fixture rows) to have something to browse. The old `prisma/dev.db` SQLite files are orphaned and can be deleted.

## Environment Notes
- Dev: `docker compose up -d db`, then `npx prisma generate` and `npx prisma db push` after pulling schema changes. `.env` holds `DATABASE_URL=postgresql://postgres:postgres@localhost:5433/speaking_finder`; `TEST_DATABASE_URL` overrides the test database (default `…/speaking_finder_test` on the same container).
- **Legacy deadline migration** (one-off, idempotent): `npx tsx server/src/scripts/shiftLegacyDeadlines.ts --dry-run` prints how many midnight-UTC deadlines without a zone would move to AoE end of day (11:59:59 UTC the next day) and get `deadlineTimezone = 'AoE'`; drop `--dry-run` to write. Against production: `DATABASE_URL="<from the Vercel dashboard>" npx tsx server/src/scripts/shiftLegacyDeadlines.ts` after the schema has deployed (the build runs `prisma db push`). Rows that already carry a time of day are left alone.
- `npm run dev` starts both servers. The desktop-app preview injects `PORT`, which the Express server also reads; start the API separately (`PORT=3001 npx tsx server/src/index.ts`) when previewing only the client.
- E2E: `npx playwright test` against the dev servers (`reuseExistingServer`). The live-search and admin-dashboard specs mock the API; the others need the real API on 3001. When 5173 is taken by another worktree's client, `PLAYWRIGHT_PORT=5174 npx playwright test` targets (or starts) a client on that port; start the preview client the same way (`npm run dev --workspace=client -- --port 5174`).
- Manual sync of one source (admin token required, or the dashboard's "Run now"): `POST /api/sync?mode=daily&scraper=confs.tech` (names: `pretalx.com`, `sessionize.com`, `linkup`, …). Without a server, `runScraper(def, 45_000)` from a `.mts` script does the same against the local DB.
- Enrichment calls that hit Claude are manual only; unit tests never call the API. A live check: `npx tsx` a script that imports `services/extraction.ts` with `ANTHROPIC_API_KEY` exported (see CHANGELOG 2026-11-02 for what was run).
- A new worktree has no `.env` and no generated client: copy `.env` from the main checkout (set `ENABLE_AUTO_SYNC=false`), run `npm install` and `npx prisma generate`; the Docker Postgres is shared by every worktree, so a schema change in one worktree is visible to the others after its `db push`.
