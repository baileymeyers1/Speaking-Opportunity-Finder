## 2026-11-24: following links, and a label where speakers pay

Step 3 of the plan in `docs/plans/2026-11-24-industry-calendars.md`. Schema: two nullable columns, `payToPresent` and `callUrl`, no default.
- **The page reader returns the page's links** (`services/pageLinks.ts`): up to 60, menus included (the text reader drops navigation, and an event's "Call for Speakers" link is usually there), calls first, then other sites, then the rest; anchors, mail, social, asset and chore links (sign-in, privacy, cart) left out. Our fetch takes them from the HTML, the Linkup reader from its raw HTML or its markdown.
- **The one extraction answers four more things**: `callPageUrl` (the event's call page when it is not this page), `officialUrl` (the event's own site when this page is a listing of it), up to 25 `listedEvents` (a directory's or calendar's events) and `payToPresent`. A URL that is not one of the page's links, or is the page itself, is dropped: the model cannot invent an address.
- **The call page is read in the same read** (`services/callFollowing.ts`): the worker's first read, every verification and live search. It replaces what the event page said only when it holds an open call; the row then applies at `callUrl` and keeps `applyUrl` (scrapers and searches find rows by it). A closed call page changes nothing: it may be last year's.
- **Official sites and listed events become `Followed Link` rows** (`services/followedLinks.ts`), hidden until read like search hits, with the page they came from in `sourceUrl`. Stored addresses, social pages and the pay-to-present aggregators are skipped; a followed page never queues another directory. The worker reads one only when the site's robots.txt allows every crawler (`services/robots.ts`).
- **"Speakers pay"** on a row, and "Fee to present" on the call page, when the page says speakers must pay a registration, publication or presentation fee. A label, not a filter (decided 2026-11-24). Apply goes to `callUrl` when there is one.
- **Measured** on 16 real pages, 17 Claude calls: one of 11 production "to watch" events had an open call on its call page (TIIKM's education conference, which also asks speakers to pay); three listed "events" were lists of events; Sovereignty Founders' energy page gave 10 events to follow, Renewables Calendar 5; a calendar entry and a pay-to-present listing named the official sites.
- **Tests.** `pageLinks`, `callFollowing`, `followedLinks` (fake database: a followed row is unread and claimable, which the shared test database must not hold), `robots`, the extraction's new fields, and live search reading a call page and queuing an official site. Server: 856.

## 2026-11-24: live search keeps more of what it finds

The second step of the plan in `docs/plans/2026-11-24-industry-calendars.md`. A search for "Energy" in California had found 43 pages, read 8 of them (3 were directory pages, 1 a funding call, 2 closed calls), and left 35 for a worker that reads 5 rows every 5 minutes. A week later every one of those rows was deleted, read or not. No schema change.
- **Live results are kept** (`services/retention.ts`, used by the daily sync's cleanup). A live result now expires like any other row: 36 hours after its deadline, unless saved. A live result that is not listed (closed, not an event, never readable) is deleted 30 days after it was found, so a later search reads the page afresh; the worker gives up on an unreadable hit after the same 30 days. Before, every unsaved live result went after 7 days, listed ones included.
- **16 reads per search instead of 8** (`SYNC_ENRICH_LIMIT`). Pages and extractions run all at once, so the request waits for its slowest hit, not their sum.
- **Event pages are read first.** `readPriority` (`liveHitTriage.ts`) puts pages that list many events last ("Energy Conferences in USA 2026-2027", "Events - …", "Calendar — …", a title spanning two years), unless the title itself asks for speakers. They are still stored and read by the worker. The aggregators of pay-to-present conferences (conferenceinusa.com, allconferencealert.com, conferencealerts.co.in, conferenceineurope.org, conferenceindex.org, waset.org) are dropped at triage, live and scheduled.
- **The worker reads a search's leftovers first and three at a time.** `claimNextUnenriched` claims live-search rows before any other unread row. The cron reads up to 15 rows a run, three side by side, none started after 35s. One local run read 15 in 30.3s.
- **Two concurrency bugs found on the way.** The daily usage counter created its row for the day with an `upsert` whose update was empty, which Prisma runs as a find then a create. The first callers of a day raced each other and all but one failed on the primary key. A live search's 8 parallel reads could already hit this just after midnight UTC. It is now `createMany` with `skipDuplicates`; the new test fails 3 runs in 3 on the old code. And `claimNextUnenriched` gave up when other workers had taken its five candidates, which would have read as "nothing waiting". It now asks again.
- **Measured.** The same "Energy" + California search on the local database: 37 candidate pages (the aggregator pages are gone), 16 read in 11.4s, 3 shown (2 before), 22 left for the worker. Most of the extra reads were energy procurement pages ("Solicitations", "RFO", "Bids & RFPs"). In energy, "call for proposals" means a request for bids, which is a fix for the query-wording step.
- **Tests.** `retention.db.test.ts` checks both cleanup rules against Postgres, read-only and scoped to its own rows. `enrichmentBudget.db.test.ts` gained the live-first claim, a batch read three at a time with each row read once, and same-moment slot reservations. The triage tests use titles from the real search. Server: 777 tests, 26 of them new.

## 2026-11-24 — Location filter matches places, not substrings

Found from a search for "Energy" in "california" that returned nothing although production lists 6 California energy calls. No schema change.
- **Why it failed.** The filter looked for the typed text inside the stored location, and extraction stores a US place as "City, ST". On the 835 cards production listed that day: "california" found 1 of 34 California calls, "texas", "florida" and "illinois" none, "USA" 25 of about 240 US calls; "CA" found 69, of which 31 were in California (the rest Canada, Chicago, Costa Rica, Caen), and "NY" 40, of which 7 were in New York (the rest mostly cities in "Germany").
- **Places** (`server/src/lib/location.ts`, tables in `lib/places.ts`). A typed place becomes a list of patterns: a US state by code (only after a comma, case-sensitive) or name (as a whole part, so "Kansas" is not found in "Arkansas"), its larger cities when a row names the city alone, the US, the UK and Canada by any of their names, a few nicknames (NYC, SF, Bay Area; "LA" is Louisiana and Los Angeles), and a short name as a word. `opportunityQuery.placeWhere` builds the SQL from the same patterns `locationMatches` checks in memory. Run over production's locations: California 36, Texas 17, USA 244, UK 32, Canada 6.
- **Online calls** are listed under a location filter too, after the calls in the place (default order and search), and every row says whether it is in the place (`matchesLocationFilter`). Browse groups the rows: in the place, "Online", then "Elsewhere" (live-search results outside the place). Before, stored rows carried no flag, so every location filter read "Nothing found in …" above an "Elsewhere" list.
- **Live search** checks its results with the same matcher (the old alias list is gone) and names the place in full in its queries ("California", not "CA").
- **Tests.** `lib/location.test.ts`; `locationFilter.db.test.ts` checks the SQL against Postgres; the lane and list-order suites scope their rows by a made-up place, and now ask for in-person rows so an online row from another suite cannot join them.

## 2026-11-20 — A roster of speakers: several profiles per account, and a Speakers page

Second of three PRs for the roster, built from a wireframe agreed the same day. Fit and saved calls per person come in the third.

- **Speakers page** (`/speakers`, the tab that was Profile; `/profile` redirects). ## 2026-11-20 — Saving a profile no longer needs one profile per account

Groundwork for the roster of speakers; nothing visible changes.
- **Why first.** The roster makes `SpeakerProfile` many per account, which drops the unique index on `userId`. Every preview build pushes its schema to the production database, so that index goes before the roster's code is merged. Rehearsed on a copy of the local database with the roster's schema: reading a profile and saving a call still worked, saving a profile failed. Prisma sends `upsert({ where: { userId } })` as `INSERT ... ON CONFLICT ("userId")`, and Postgres rejects that (42P10) once no unique index covers the column.
- **Fix.** `profileService` reads the account's oldest profile row and then creates or updates by id. Same behaviour while the index exists; it keeps working once it is gone.
- **Also learned in the rehearsal.** `prisma db push` refuses to add a unique constraint to a table without `--accept-data-loss` (which the CLI will not take from an agent), so the roster's "one saved row per call per person" is kept by the code and a plain index, not a new constraint.

## 2026-11-19 — Functions next to the database; a live search answers in about half the time

A test search on production took 27.2s. Its request log, step by step: Linkup search 2.7s, reading eight pages (all refused, so through the reader) 8.9s, Claude 4.6s, storing 20 new hits 10.7s, building the reply 0.5s.
- **Root cause of the largest part.** The functions ran in Vercel's default region, `iad1` (Washington, D.C.), and the database is Render's Oregon region, so every query was a round trip across the country. Storing a hit and matching it to a canonical event is about five queries, one after another: 0.53s a row. The same latency is behind the sync writes that overran the 60s limit before 11-16.
- **`vercel.json` `regions: ["pdx1"]`.** Measured from the US east coast, production in `iad1` against the preview in `pdx1`, eight runs each: default list of 20, 0.48s → 0.33s; list of 100, 0.53s → 0.43s; filter options, 0.32s → 0.25s; `/api/health`, which makes no query, 0.10s → 0.19s, because an east-coast caller is now the far end. Server time for the list is about 130 ms. Storing a live hit: 0.53s → 0.17s a row.
- **Per-hit pipeline.** A live search read all eight pages, waited for the slowest, then sent the eight to Claude. Each hit now reads its page and is extracted in one go, all at once. `extractOpportunitiesBatch` had no other caller and is gone.
- **Event matching left to the worker for unread hits.** The request matched every stored hit to an event, most of them hits nobody had read and nobody can see. It now matches the hits it read; `assignEventIfMissing` in the worker matches a row when it has read it and found it to be an event, under its cleaned-up title. That also picks up rows a killed sync left without an event, and stops creating events for hits that turn out not to be events.
- **Measured on previews against the production database** (three different queries, so orders of magnitude, not a controlled comparison): 27.2s before; 15.2s with the region and the pipeline (25 hits stored in 4.3s); 11.4s with the matching deferred as well (12 hits stored in 1.5s). ## 2026-11-02 — P0 data-integrity fixes in sync and enrichment

- **Re-scrapes no longer wipe enrichment.** `persistResults` built one `data` object for create and update that set `enrichmentStatus/enrichedAt/enrichmentError` to `null`, so every daily sync re-queued every enriched row and overwrote Claude's cleaned title, organization, dates and location.
