## Tier 1: accuracy — trust is the product

### 1. Verify every listing against its own page, on a schedule
**Problem.** Today a row is checked once, when it is scraped or live-searched. CFPs close early, dates move, pages 404. Users click through to dead calls and stop trusting the list.
**Addition.** A `verifiedAt` column and a verification pass in the enrichment worker: re-fetch `applyUrl`, run the existing Claude extraction (`liveSearchService.extractMetadataWithClaude` already does this well for live results), update `isClosed`, dates, location; mark 404/410 as closed. Re-verify rows with a deadline inside 14 days every 2 days, others weekly. Show "Verified 3 days ago" on the card.
**Why first.** It reuses the page-fetch + extraction path that already exists for live search, turns the enrichment cron into a freshness engine, and is the single biggest lever on accuracy. It also lets you unify the two enrichment paths (review step 4).

### 2. Structured extraction with a schema, plus confidence
**Problem.** Both Claude calls parse JSON out of free text with a regex and accept whatever comes back. Dates are the most common error class in the git history.
**Addition.** Use structured outputs (`output_config.format` with a JSON schema) for both prompts so the shape is guaranteed, and ask for a `confidence` (high/medium/low) and `evidence` snippet per date field. Store confidence; show low-confidence dates as "~Dec 1" and exclude them from "closing soon" alerts.
**Why.** Removes a whole class of silent parsing failures and gives the UI an honest way to show uncertainty instead of a wrong date.

### 3. One canonical event across sources and years
**Problem.** The same conference appears from confs.tech, WikiCFP and Linkup with different URLs, and again next year. Cross-source dedup matches on a 10-character org prefix.
**Addition.** An `Event` entity (name, organizer, canonical domain, recurring edition) with `Opportunity` rows attached per year/source. Match on normalized name + domain, fall back to Claude for ambiguous pairs. Show one card with "also listed on WikiCFP" and prior-year dates as a hint for when next year's CFP opens.
**Why.** Dedup is the second most common complaint class in a multi-source aggregator, and the recurrence data is the basis for "expected to open in March" predictions, which no competitor does well.

### 4. Correct deadline semantics
**Problem.** Deadlines are stored as UTC midnight, so a US deadline shows as expired the evening before; "Anywhere on Earth" deadlines are common in academic CFPs.
**Addition.** Store deadlines as end-of-day in the event's timezone (default AoE, UTC-12), display in the user's timezone with "closes in 3 days, 11:59 PM AoE". Add a `deadlineTimezone` column; let the extraction prompt fill it.

## Tier 2: usefulness — from list to workflow

### 5. Saved-search alerts by email — deferred (soon)
**Problem.** `SavedSearch` exists but nothing happens when new matches arrive. Password reset also has no email. Users have to remember to come back.
**Addition.** Add a transactional email provider (Resend or Postmark). A daily digest cron: for each saved search, run the filter against rows created or verified since the last digest, send if non-empty. Reuse the same provider for password reset. Unsubscribe link and per-search toggle.
**Why.** Alerts are what turn an aggregator into a habit. Everything but the email send already exists.

### 6. Application tracker and in-app deadline calendar — deferred (later)
**Problem.** `SavedOpportunity.category` is a flat tag. Speakers manage pipelines in spreadsheets.
**Addition.** Status pipeline on saved items (interested → drafting → submitted → accepted / declined), a `submittedAt` and notes field, and an in-app calendar view of deadlines and event dates (decided 2026-11-03: no ICS feed). Reminders at 7 and 2 days before a deadline via item 5.
**Why.** Low effort on top of the existing model, high retention.

### 7. Speaker profile and match score
**Problem.** Relevance is a keyword hit count. Everyone sees the same ranking.
**Addition.** A profile with topics (free text + tags), seniority, home city, travel radius, remote preference, compensation requirement. A `matchScore` per opportunity computed server-side (topic overlap via embeddings or a cheap Claude classification on the profile, cached per opportunity) blended with quality score. Sort by "best match", explain the score on the card ("matches: healthcare, Denver, travel covered").
**Why.** This is the difference between a search engine and a recommendation engine. Embedding the ~hundreds of active rows once is cheap.

### 8. Live search that feels instant and gets better over time — first half shipped
**Problem.** A live search runs a 60-second pipeline inside the request and the auto-save is killed by the serverless freeze, so the work is thrown away.
**Addition.** ~~Return Linkup hits fast, persist them immediately as unenriched, and let the enrichment cron finish them~~ (shipped 2026-11-02, PR #3). Remaining: record every search query in a `SearchLog` table and promote frequent queries into the scheduled Linkup slice, so the stored catalogue grows toward what users actually ask for.
**Why.** Turns wasted spend into permanent coverage and fixes the slowest interaction in the app.

## Tier 3: coverage — more real sources, fewer fake ones

### 9. Pretalx and Sessionize as first-class sources
Most tech and community conferences run their CFP on one of these. Pretalx instances expose a public JSON API per event (`/api/events/`), and many organizers host on `pretalx.com`; Sessionize has a public "discover" listing. Add a scraper per platform with fixture tests like the ones added for conferenceAlerts. These two would likely exceed the row count of every current structured source combined.

### 10. Podcasts and non-conference formats
The UI advertises podcasts, webinars and panels; the data has almost none. Options: PodMatch / MatchMaker.fm listings (guest calls) and a Linkup query set tuned for "looking for podcast guests", "call for speakers meetup", "lightning talks wanted". Label format accurately rather than defaulting to "conference".
**On Luma and Meetup.** Both list events for attendees, not calls for speakers, their listing pages are JavaScript-rendered or need an API key per calendar, and a "speakers wanted" meetup is rare among thousands of ordinary events. They only pay off as a discovery source behind a Claude "is this seeking speakers?" filter, so they are a later addition, not a first source.

### 11. Admin dashboard rework (decided 2026-11-03: a deep rework, not one panel)
`ScraperRun` now records every run. Surface it: last run, rows found, error, and a sparkline of found-per-run. A source that returns 0 three times in a row should show red. This is how the dead-scraper problem gets noticed in a day instead of seven months.
