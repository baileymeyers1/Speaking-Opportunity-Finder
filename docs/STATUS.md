## What's Working
- Browse, filters, saved opportunities, saved searches, auth (JWT cookie).
- **Database: Postgres everywhere.** `docker compose up -d db` starts `postgres:16` on host port 5433 with `speaking_finder` (dev) and `speaking_finder_test` (vitest). One schema, `prisma/schema.prisma`; `prisma.config.ts` holds the schema path and `DATABASE_URL` for the CLI. The Prisma 7 client is generated into `server/src/generated/prisma` (gitignored; `npx prisma generate`), imported from there, and built once in `server/src/lib/prisma.ts` on `PrismaPg` (a lazy `pg` pool). `tsc` compiles the generated TypeScript into `server/dist`; the query compiler is a base64 WebAssembly import from `@prisma/client/runtime`, so the Vercel function needs no extra files. Search is case-insensitive (`mode: 'insensitive'`, no provider sniffing); the list is filtered by sector (`sectors`, a native `text[]` with a GIN index), not by the free-text `industries` JSON string. `lib/databasePool.ts` turns verified TLS on for any non-local host (the Render database refuses plaintext, which `pg` would otherwise send) and leaves the Docker database on plaintext; an `sslmode=` in the URL overrides it.
- **Server tests against a real Postgres.** `server/vitest.config.ts` points `DATABASE_URL` at the test database and a global setup pushes the schema into it; `enrichmentBudget.db.test.ts` exercises the budget counter and the claim lock for real and `persistResults.db.test.ts` the sync's writes and deadline; every other suite mocks `lib/prisma.js`.
- **Admin dashboard** (`/admin/dashboard`, `client/src/components/admin/`): an attention strip derived on the client (`attention.ts`) from the sources and pipeline responses, then Sources (status, last run, 14-day sparkline, row counts, "Run now" via `POST /api/sync?mode=<cadence>&scraper=<name>`), Pipeline (unenriched backlog, claims and stale claims, failures, verification due per `verification.ts`, today's budget meter, cron liveness, last 10 events, "Run enrichment batch now" via `POST /api/admin/enrichment/run`), Catalogue (active rows by format, sector, top tags, deadline bucket, remote; how many have no sector) and Demand (saved-search filters plus the live-search log's 7/30-day totals and top queries). Endpoints: `GET /api/admin/analytics/{sources,pipeline,catalogue,demand,search-log}` in `server/src/services/analytics/`, typed in `shared/admin.ts`. Red conditions: a source with 3 consecutive empty/error runs, budget exhausted, any stale claim, >50 rows overdue for verification, daily sync older than 26h, weekly older than 8d, enrichment older than 15 min while work is queued.
- **Hosting: Vercel only.** The old Render web services were deleted on 2026-11-19; the Postgres is the one thing left on Render. Express runs as one serverless function; Vercel Cron drives syncs and enrichment, and nothing else schedules them: off Vercel `server/src/index.ts` only listens (locally, run a sync from the admin dashboard or `POST /api/sync`). The functions run in `pdx1` (Portland; `regions` in `vercel.json`), the same region as the Render Postgres (Oregon). In Vercel's default `iad1` (Washington, D.C.) every query crossed the country. Measured 2026-11-19 from the US east coast, production in `iad1` against a preview in `pdx1`: the default list of 20 answers in 0.33s instead of 0.48s (about 130 ms of server time), the filter options in 0.25s instead of 0.32s; a request with no query, like `/api/health`, takes 0.19s instead of 0.10s, because the caller is now the far end. Moving the database east instead would make both ends close for an east-coast audience; that is a migration, not a setting. The build runs `prisma generate`, `prisma db push` against the production `DATABASE_URL`, then `npm run build`, so schema changes deploy themselves (preview builds included).
- **Scrapers** (registry in `server/src/scrapers/index.ts`): confs.tech, javaconferences.org, callingallpapers.com, developers.events, pretalx.com, sessionize.com, ruralhealthinfo.org, radioguestlist.com, linkup (daily); wikicfp.com, conferencealerts.com (weekly). papercall.io was removed: the domain no longer resolves. Each run persists its own rows and is recorded in `ScraperRun` (surfaced by `GET /api/admin/analytics/sources`; a source missing from the registry shows as retired). Syncs take a time budget (50s under cron) and run least-recently-run sources first, so nothing starves. The budget bounds each scraper's fetch *and* its writes (`scrapers/persistResults.ts`): stored rows are looked up in one query, new rows are written first, refreshes of stored rows run 5 at a time, and what is left at the deadline is logged as "left for the next run". Each write was a ~100 ms round trip from the function to the database while the functions ran in `iad1`, which is why one-at-a-time writes overran the function; from `pdx1` it is about a third of that (Hosting).
- **Pretalx** (`scrapers/pretalx.ts`): `GET {instance}/api/events/` is a flat public list (pretalx.com: 755 events, ~83 upcoming); each upcoming event's `/{slug}/cfp` page gives open/closed (the submit button) and the deadline (a localized status line). Instances: pretalx.com and pretalx.c3voc.de. Live 2026-11-03: 39 open calls in 3.5s. The API has no location; enrichment fills it.
- **Sessionize** (`scrapers/sessionize.ts`): the Discover listing needs a login, but `sitemap/events.xml` lists ~11,000 public event pages newest first and each page states CFP open/close dates, event date(s), location and website. Each run reads the newest 80 pages; recurring user groups are labelled `meetup`. Live 2026-11-03: 74 open calls (56 conference, 18 meetup) in 3.0s.
- **Rural Health Information Hub** (`scrapers/ruralHealthInfo.ts`, source `ruralhealthinfo.org`): the federally funded hub's staff-kept list of health events with an open call for presentations (`/events/calls`, 10 a page, followed through the pager). Each entry gives the event, dates, organizer, venue, city and the call with its submit link and deadline; the deadline is read as end of day AoE (no zone stated). One row per event: the first call that is not for posters alone. The apply URL is the call's link, or the event page when that link is a PDF (persistence drops file URLs, `isFileUrl`) or another event already uses it. Live 2026-11-18: 20 events, 19 rows, all `conference`, all with deadline, event date and a US city, in 0.7s. 11 of the 19 apply pages read with the plain fetch; the rest are form shells (Qualtrics, monday.com, Whova, a Google Drive file), a 403 and a timeout, and those rows are enriched from the listing text.
- **RadioGuestList** (`scrapers/radioGuestList.ts`, source `radioguestlist.com`): podcast, web and radio shows post what guests they are looking for; the feed (`/guestrequests?format=rss`) carries the 20 newest, about one new request a day. The parser splits each post on the site's form labels (show, description, guest request, formats, fees); a label it does not know opens an ignored field. Rows are `podcast` (`other` when every listed format is broadcast radio or TV), remote, tagged from the site's categories, `compensationType: exposure`, with no deadline: the row links to the request page, which holds the booking contact (never copied into the description), and verification closes the row once the site takes the page down (its sitemap holds 45 requests, none older than five weeks, though they are numbered up to #8273). Shows that name a price for the interview are left out, as are the sponsored guest profiles in the same feed. Live 2026-11-18: 19 requests, 3 charge guests, 16 rows in 0.5s; all 16 request pages read.
- **Linkup query set** (`scrapers/linkupQueries.ts`, 110 queries): 89 industry conference queries plus a format group (8 podcast guest calls, 6 meetup/user-group, 4 webinar, 3 panel), each stored with its `format`. The daily run takes a 6-query rotating slice plus up to 2 promoted queries. Hits go through the live search's triage before they are stored (`liveHitTriage.looksLikeArticle`: article titles, and forum and social hosts such as linkedin.com, which are never an event's own page); "CFP" in the text counts only as a word, not as the financial-planner credential "CFP®".
- **Search log** (`services/searchLog.ts`, model `SearchLog`): both live-search controllers await one insert per search (query normalized, industries/locations JSON, result count, user id when signed in). `promotedLinkupQueries` returns the most frequent normalized queries of the last 30 days, searched at least twice and not in the static set, as `"<query> call for speakers CFP <years>"`. `GET /api/admin/analytics/search-log` (`analytics/searchLog.ts`) returns 7/30-day totals and the top queries, which the admin Demand section renders.
- **One extraction call** (`server/src/services/extraction.ts`, Anthropic SDK 1.x, API version 2026-10-21): structured outputs (`output_config.format`, strict JSON schema) on `claude-haiku-5-5` return typed dates, location, closed/relevant flags, compensation, format, industries, cleaned title/organization and a high/medium/low confidence per date field. `mergeExtraction` holds the single set of merge rules. Enrichment, verification and live search all go through it.
- **Sectors** (`server/src/lib/sectors.ts`: 34 ids with labels, tech and non-tech, PR & Communications apart from Marketing & Advertising; the client reads the file by path). Every row carries zero, one or two in `Opportunity.sectors`. Claude names them in the one extraction call (an enum array in `EXTRACTION_SCHEMA`; the prompt lists `id: label`; `parseExtractionOutput` drops unknown ids and cuts at two, since structured outputs do not enforce array lengths). Rows Claude has not read are placed by their tags with no model call (`services/sectorMapping.ts`: longest phrase first, so "food security" is agriculture and "software supply chain" is security; `sectorPhrases.ts` holds the phrases, `sectorBroadWords.ts` the words that decide nothing alone: "communications", "technology", "management", "architecture" only add weight to a sector another tag already names). Precedence in `mergeExtraction`: Claude's sectors, else the ones the row has, else the tags. Scrapers and live search store mapped sectors (`persistData.ts`); a re-scrape never replaces an enriched row's sectors; enrichment and every verification write what Claude named, so the weekly re-check replaces mapped sectors at no extra call. Filter: `?sectors=<id>` (any of), `hasSome` on the array; an old `?industries=` value or saved search is mapped to its sector on the server (`controllers/opportunityFilters.ts`), one no sector matches is ignored. `GET /api/opportunities/filters` returns all 34 sectors with their listed counts instead of every tag. A selected sector is enough to run a live search (its `searchTerm`). Cards and the detail page show the sector before the tags; the admin Catalogue counts by sector and shows how many rows have none.
- **Deadline semantics** (`server/src/lib/deadlines.ts`, pure, also imported by `client/src/lib/dates.ts`): a CFP deadline is a calendar day in a zone, stored as the instant that day ends (`endOfDayInZone`) with the zone in `deadlineTimezone` (IANA name or `AoE`; null = not stated, read as AoE, UTC-12, the most lenient reading). The extraction returns `cfpDeadline` + `cfpDeadlineTime` + `deadlineTimezone` (never inferred from the venue); scrapers go through `endOfCalendarDay`; Pretalx uses the event's API `timezone`, Sessionize the exact closing instant it embeds (`Etc/GMT±N`), callingallpapers its ISO offset. `deadlineInstant` reads a not-yet-migrated midnight-UTC row as AoE end of day, so nothing expires early before or after the migration. `cleanupExpired` only deletes rows closed for 36h+. Cards show "3d left" with the closing time in its zone and on the viewer's clock on hover; the detail page shows "Monday, November 30, 2026, 11:59 PM AoE · Dec 1, 3:59 AM your time".
- **Page reader** (`services/pageReader.ts`, `readPage`): the worker, verification and live search all read a page through it. Our own fetch goes first (`pageText.ts`, 8s, 5000 visible chars). When that is refused (any HTTP error but 404/410), gets a file that is not HTML (a PDF call), gets an empty JavaScript shell or times out, the page is read through Linkup's fetch endpoint (`POST /v1/fetch`, the same `WEB_SEARCH_API_KEY` as search): HTML through the same `visibleText`, anything else as the reader's markdown. JavaScript rendering is asked for only after an empty shell ($0.005 a call against $0.001; a failed call costs nothing). Not for a gone page, and not for a host that cannot be reached. A sign-in or anti-bot page is not counted as read (`looksLikeChallengePage`). Every attempt counts against a daily cap of 300 (`PAGE_READER_DAILY_LIMIT`, 0 turns the reader off), a row of `EnrichmentUsage` keyed `<date>:reader`. When the reader cannot read the page either, the first failure stands with the reader's reason added (`HTTP 403 (reader: FETCH_TARGET_NOT_FOUND)`), so a search hit stays unread as before. Measured 2026-11-19 on one page from each of the 30 hosts that blocked us most: our fetch read 2, the reader 20 more without JavaScript, 1 more with it (a sign-in page, now rejected), 7 not at all (luminik.io, infosec-conferences.com, hr.com, app.advocu.com among them). Read end to end on 12 real pages: two directory pages came back "not an event" and drop out, three calls came back open with a deadline (a privacy symposium, RE//verse, the IEEE Aerospace call, which is a PDF).
- **Background enrichment** reads `applyUrl` first (`readPage`, above) and extracts from the page text; a 404/410 closes the row without a Claude call. DB-backed daily budget (600 calls by default, `ENRICHMENT_DAILY_LIMIT` overrides), per-row claim lock, 3 retries, 50s time budget per cron run. Re-scrapes preserve enriched fields. Cleanup never deletes saved rows. Closed/irrelevant rows are flagged in columns and hidden. A page with under 100 characters of visible text is the empty shell of a JavaScript app (app.advocu.com: 6) and counts as not read (`pageText.ts`, reason `empty`). When the page cannot be read, a row from a CFP listing is extracted from its listing text as before; a search hit gets no Claude call and is marked `skipped` with `page unreadable: …` (`planEnrichment`).
- **Scheduled verification** (`services/verification.ts`): once no unenriched rows remain, the same cron re-checks stored listings against their page. Deadlines within 14 days are re-checked every 2 days, everything visible weekly; dates, location, remote flag, compensation and `isClosed` follow the page; `verifiedAt` / `verificationError` / `dateConfidence` are stored. Same daily budget. Search hits and listed calls differ (`searchSources.ts`): for a search hit the page is the only evidence, so `isRelevant` and `hasOpenCall` follow every read (a directory judged relevant once is dropped at its next check); for a row from a CFP listing relevance stays as enrichment set it and a page can confirm the call but not deny it (`hasOpenCall` true or back to null). Rows with no deadline whose event has passed are not checked. A search hit enrichment could not read is retried here for 30 days (`UNREADABLE_GIVE_UP_DAYS`), and the first successful read enriches it in full (`buildEnrichmentUpdate`).
- **Live search** runs three Linkup queries in parallel ("call for speakers", "call for proposals / submit a session", "speakers wanted / podcast guest / panel / webinar"; each names this year and next, abbreviations like PR spelled out), dedupes by URL, drops hits whose snippet or title dates the event in the past, keeps hits containing every query word (or its synonym, `searchTerms.ts`), and drops article titles (`liveHitTriage.ts`). In-request reads go to hits that look like a call first (`callSignal`). Hits already stored are listed from the database (enriched, grouped) and never read again; the in-request budget of 8 page fetches + extractions goes to the best new hits. Calls the new hits leave over read hits an earlier search stored but nobody has read yet (`enrichRowsNow` in `backgroundEnrichment.ts`: the worker's own claim and attempt counter, so a row is never read twice; counted in today's usage but not refused at the daily limit, since a search caps itself at 8). Only hits Claude read are returned; the rest are stored as `source: 'Live Search'`, hidden from every list until enriched (a failed or skipped read stays hidden too: it would be a snippet-only card), and listed by title in `pendingLiveHits` ("N not checked yet"). A hit whose page cannot be fetched is not extracted from its snippet: it is stored unread and counts among the unchecked. Spare calls also read waiting hits the scheduled search stored. `backgroundChecksResumeAt` tells the page when the worker resumes if it has spent the day's limit. `liveFoundCount` / `liveNotOpenCount` explain a short list ("found 26 pages; 21 weren't open calls"); `services/liveSearchHits.ts` holds these lookups. Each hit reads its page and is extracted as soon as that page arrives, all eight at once (`enrichResultsFromPages`), and only the hits read in the request are matched to an event there; the worker matches the rest when it reads them (`assignEventIfMissing`). Where the time goes, from the request logs of three test searches on 2026-11-19 (different queries, so read them as orders of magnitude): before, on production, 27.2s (search 2.7, eight pages 8.9, Claude 4.6, storing 20 hits and matching each to an event 10.7); with the functions in Portland and the per-hit pipeline 15.2s (search 2.5, pages and Claude together 8.3, storing 25 hits 4.3); with the matching left to the worker as well 11.4s (search 2.6, pages and Claude 7.1, storing 12 hits 1.5). What is left is the search itself, the pages and Claude.
- **Format** is what the page says the event is, once the page was read. The prompt defines it as the kind of event the speaker would appear at, not the kind of session asked for (a conference's call for panels is a conference). `mergeExtraction` keeps the source's format when Claude answers "other"; `buildEnrichmentUpdate` writes it only when the page was read, `buildVerificationUpdate` at every check, and a re-scrape no longer resets an enriched row's format (`persistData.ts`). So stored rows get theirs at their next weekly check. Measured 2026-11-19 on 57 listed rows read with the new prompt: 11 labels change, and mostly towards "conference" (4 Sessionize "meetups" and 4 "webinar"/"panel" search hits are conferences; 3 conferences are workshops). The labels were wrong in both directions; the share of conferences does not fall (42 of 57 before, 47 after).
- **Default order** (`compareByClosing` in `services/opportunityQuery.ts`): soonest to close first, where a row closes at its deadline, with none at its event date (a call cannot outlive its event), and with neither (a rolling call, 80 of 715 cards on 11-19) `ROLLING_CALL_HORIZON_DAYS` = 30 days from now. Ties go to quality, then id. Sorted in memory over the matching ids (four columns each), then the page's rows are loaded, so totals and pages stay exact. Before, sorting on the deadline column put all 169 cards without a deadline after the last dated one: the first sat at position 547, page 28 of 36. The event-date, quality and match sorts are unchanged.
- **What is listed** (`listedConditions` in `services/opportunityQuery.ts`; the same rule in SQL in `eventContext.shadowedEditionIds` and for one row in `searchSources.isUnreadSearchHit`): not closed, relevant, deadline open or absent, quality 15+, and since 2026-11-18 two more conditions. A search hit, live or scheduled (`Live Search`, `Linkup Search`), is listed only once its own page was read: `enrichmentStatus = 'enriched'`, `verifiedAt` set (only a page read sets it) and no `verificationError` from the last check. And a row with no deadline drops out once its event date has passed. A row from a CFP listing is not hidden by a failed check: the listing vouches for it. The filter options and the admin catalogue and per-source "active" counts use the same rule.
- **Events without an open call** are listed, not hidden: extraction answers `isRelevant` (the page is about one specific event or program) and `hasOpenCall` (it invites speakers now) separately. `hasOpenCall: false` rows show a "No open call" badge and a "View event" button, lose 15 match points ("no open call found"), and are re-verified like any listed row, so they become open calls once the page posts one. Null = not judged (scraped CFP sources, older rows): treated as open. `server/src/scripts/requeueHiddenEvents.ts` re-reads search hits hidden under the old rule (see Environment Notes).
- **Search text** (`services/searchTerms.ts`): split into words, stopwords dropped ("for", "the"); every word, or one of its synonyms (PR → public relations, comms, corporate/strategic/marketing communications; AI → artificial intelligence, GenAI; a short fixed list), must appear in the title, organization, industries or description. Words of 3 characters or fewer match whole words only ("ai" ≠ "said", "pr" ≠ "April"); longer words match a word start ("speak" → "speakers"). Same rule for the stored search and the live relevance check.
- **Client** shows "Verified Xd ago" on cards and the detail page, and renders low-confidence dates as "~Dec 1, 2026" with a tooltip (`components/VerificationHints.tsx`).
- **Client data flow:** the URL is the only filter state (`client/src/filters/serialize.ts`); TanStack Query owns fetching and caching (`client/src/hooks/`), with public lists persisted to localStorage for instant cold starts. Same URL = same cache key, so back navigation restores the prior list and any filter change refetches, live results included. Live search is a mutation that replaces the list entry for its filters.
- **Browse: a sentence, three lanes, rows.** The list is paged one lane at a time (`lane=closing|open|watch`; `server/src/services/lanes.ts`): `closing` is an open call with a deadline, `open` an open call with none, `watch` an event whose page has no call (`hasOpenCall` false). A row nobody judged counts as an open call. Closing is ordered by deadline, the other two by event date (undated last, then quality). Every list response carries `lanes`: the count of each lane under the other filters, how many deadlines fall within 7 and 30 days, and the call that closes first; a request with no `lane` still lists everything together. The controller no longer re-sorts stored rows (it used to push undated rows to the foot of each page and a search's hits out of relevance order): what the live search surfaced leads, then the service's order. Client (`client/src/components/browse/`): `SituationLine` (the headline, from `lib/situation.ts`), `LaneSwitch` (the kit's glass segmented control, lane in the URL as `lane=`), `SectorStrip` (the busiest sectors as toggles, all 34 behind a popover), `CallList` and `CallRow`. A row leads with `Countdown` (`lib/callState.ts`: days left on the deadline's own calendar; red within 7 days unless the date is approximate, which is marked "~" and stays ink). The title link covers the row. `OpportunityCard` stays for Saved.
- **Look: JCI Intelligence kit v0.4.2** (`~/projects/jci-brand-kit`, `BRAND.md` there is the reference). Tokens for both themes in `client/src/styles/tokens.css` (R G B channels, the kit's hex beside each); `tailwind.config.js` maps the shadcn names onto them, plus `good` / `warning` / `critical` / `info`, radii (`rounded-lg` 14px sheets, `rounded-md` 10px controls, `rounded-sm` 6px tags) and shadows. `client/src/styles/jci.css` holds what utilities cannot say: the button's pointer fill, the field halo, the glass bezel, the theme reveal. Outfit and Fraunces italic are self-hosted (`@fontsource-variable/*`). Header: `Lockup` (the kit's mark, `client/public/jci-logo.svg`, never redrawn), `NavTabs` (one red rule on springs), `ThemeSwitch` (the kit's glass knob; `client/src/vendor/jci/liquid-glass.js` is the kit's file byte for byte, `lib/glass.ts` hands it the springs from `lib/motion.ts`; the new theme opens from the knob by a view transition, `lib/themeReveal.ts`). Status is an icon plus a word with the colour on the icon; red is for the primary action, focus, the current tab and urgent deadlines, never a data mark or an inline link (`.link` is ink). No hard-coded Tailwind palette colour is left in `client/src`.
- **Shared wire types** in `shared/types.ts`, re-exported by the client and used to type the server's opportunity responses. `npm run lint` (ESLint 9, root `eslint.config.js`) passes; client unit tests run under `TZ=America/Los_Angeles` so UTC date formatting is asserted.
- **Canonical events** (`Event` model; `services/eventMatching.ts` pure, `services/eventAssignment.ts` DB, `services/eventContext.ts` list/detail): `normalizeEventName` strips years ("2027", "'26", "ScanAgile27"), ordinals, trailing edition numbers and listing words (CFP, Edition, "@ Sessionize.com"); `scoreCandidate` is 0.75 × name similarity (token Jaccard + bigram Dice + containment) plus a shared event domain (+0.15; shared platforms such as sessionize.com, pretalx.com, meetup.com, linuxfoundation.org, gitnation.com count for nothing), organizer (+0.05), event dates (+0.10 within 45 days, +0.07 about a year apart, −0.05 otherwise) and city (±0.05); a name below 0.7 can never auto-link, and neither can a pair `autoLinkObjection` rejects: the shorter name's distinctive words must all be in the longer one, extra words must be an acronym or a place, parenthesised acronyms must agree and the locations must share a place word (production dry run false positives, 2026-11-04). ≥ 0.80 links, 0.55–0.80 is recorded on the row as `possibleEventId`/`possibleEventScore` and left apart (no Claude call: a same-event question does not fit the page-extraction prompt), below that is a new event. Candidates come from a GIN-indexed `nameTokens String[]` overlap plus the domain. Scrapers and save-live assign events to new rows inside the request; a live search does so for the hits it read, and the worker gives a row its event when it reads it and finds it to be one (`assignEventIfMissing`), which also picks up a row a killed sync left without one. `editionYear` comes from the event date, else the title. Default list: one card per event (the visible edition with the nearest open deadline; hidden ids come from one SQL window-function query, so totals and pages stay exact), `alsoListedOn` and `previousEditions` on each item, `eventEditions` on the detail response.
- **Speaker profile and match score.** `SpeakerProfile` (one per user: topics, bio, seniority, home city/country, travel radius, remote preference, compensation requirement, preferred formats) is edited at `/profile` and stored via `GET/PUT /api/profile` (zod-validated, `services/profileService.ts`). `services/matchScore.ts` scores a row 0..100 from the profile alone, no model call: topic overlap (whole-word, case-insensitive, plural-tolerant, against industries + title + description), location fit (remote preference, same city/country, travel radius; "City, ST" counts as US), compensation fit, format fit, each counted only when the profile states it; 20% quality blended in; small penalties for a deadline inside 3 days, a low-confidence deadline and an unverified row. Reasons ("matches: devops", "in Denver", "travel covered") and misses ("in-person in Berlin, you prefer remote") travel with the row. The list and detail routes read an optional token; `sort=match` scores a quality-first candidate set of up to 500 rows in memory and paginates it. Client: "N% match" popover on cards, "Why this matches" on the detail page, "Best match" in the sort select once a profile exists; login/logout/profile save drop cached lists so scores never leak between users.

## Deploy Gotchas
- Every Vercel build, previews included, runs `prisma db push` against the production database. Before pushing a branch with a schema change, diff it against production: `vercel env pull --environment=production <file>`, then `npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema prisma/schema.prisma --script` must print an empty migration (or exactly the additive change you intend). A destructive change makes the build fail (no `--accept-data-loss`), it does not drop data.
- **A new column that holds data blocks every branch that lacks it.** `prisma db push` from a schema without the column drops it silently while every value is NULL, and fails the build ("about to drop the column … which still contains N non-null values", nothing lost) once one row holds a value; an empty array counts. Tested on a scratch database, 2026-11-18. So a list column gets no `@default` (a default fills every existing row at once: `sectors` is declared without one), and between a branch's first preview build and its merge nothing may write the column: no backfill against production, no live search or save through the preview. After the merge the enrichment cron writes it within minutes, and every branch that predates the merge fails its build until rebased onto `main`. `sectors` was added this way (PR "sectors"): its build runs `ALTER TABLE "Opportunity" ADD COLUMN "sectors" TEXT[]` and `CREATE INDEX "Opportunity_sectors_idx" ON "Opportunity" USING GIN ("sectors")`; the sector backfill (Environment Notes) runs only once the PR is on `main`.
- `prisma` on npm has an 8.0 release candidate as `latest`; `prisma`, `@prisma/client` and `@prisma/adapter-pg` are pinned to `^7.10.1`. Prisma 7's CLI refuses `db push --accept-data-loss` and `--force-reset` when run by an AI coding agent; run those from your own terminal.
- Request logs (`pino-http` in `server/src/app.ts`) write only method, URL, `user-agent`, `x-vercel-id`, `x-vercel-cron-schedule` and the status code (`lib/requestLogSerializers.ts`). Until 2026-11-16 they wrote every header, so `CRON_SECRET`, Vercel OIDC tokens and users' JWT cookies sat in the runtime logs (1-day retention): `CRON_SECRET` was rotated on 2026-11-19 (Vercel Cron got a 200 with the new one at 16:40 UTC; a request without it gets 401). Don't widen the allow-list to credential headers.
- The database password was rotated on 2026-11-19: a new default credential in Render (database Info page, Credentials), `DATABASE_URL` updated in Vercel for all three environments, production redeployed, then the old credential deleted (it now answers "role is not permitted to log in"). A new credential leaves the old one valid until it is deleted, so update Vercel and redeploy before deleting.
- Env vars live in the Vercel dashboard: `DATABASE_URL`, `JWT_SECRET`, `CRON_SECRET`, `ANTHROPIC_API_KEY`, `WEB_SEARCH_API_KEY` (Linkup: search and the page reader). Optional: `ENRICHMENT_DAILY_LIMIT`, `PAGE_READER_DAILY_LIMIT`. No `CLAUDE_MODEL` override is set; if you add one it must be a current model (the request sends `output_config.effort`).
- The team is on Vercel Pro, so the 5-minute enrichment cron runs as declared (verified 2026-11-03: ~12 invocations/hour in runtime logs). Express trusts Vercel's proxy (`trust proxy` when `VERCEL` is set) so rate limiting keys on the real client address.
- `npm audit` still reports 18 advisories (16 moderate, 2 high), all behind major bumps that were deliberately not taken here: react-router-dom 7 (open redirect / SSR hydration in react-router 6), Vite 8 (dev-server path traversal, `launch-editor` on Windows, the esbuild dev-server CORS issue), ESLint 10 / typescript-eslint and nodemon (the `minimatch` globparts DoS), and `picomatch` 2.x reached through Playwright.
